延迟线真正有意思的地方，是它的长度可以变化。这篇文章会从我为 Dreamcatchers 制作的固定延迟“拉线电话”开始，再用同一套环形缓冲区思路，逐步实现一条平滑的可变延迟线。

固定延迟

最近我在制作 Dreamcatchers 时，实现了一个带有固定时长延迟的“拉线电话”。玩家的实时语音数据进入缓冲区后，系统会先等待 X 时间，再把它播放出来。

这个效果自然有两种实现方式。第一种最直接：加一个计时器，等它结束后再把音频数据送入输出缓冲区。它很简单，但会严重依赖游戏主线程的计时。如果主线程因为处理繁重的渲染任务而掉帧，计时结果就可能不准确。这和 Unity 里的情况完全一样：如果你需要采样级精确的时间，就不应该依靠 Update() 来计时。

第二种方式是使用环形缓冲区。如果你熟悉音频编程，这几乎就是默认做法。我们准备一个容量等于最大延迟的数组，再维护延迟采样数 X、读指针和写指针。读指针先取出数组里的历史采样，写指针随后用新数据覆盖同一个位置。只要让读指针始终落后写指针 X 个采样，就能得到 X 个采样的延迟。

C++ 
class FixedDelay
{
public:
    FixedDelay(...) // 传入初始化成员所需的参数
    {
        // 动态分配历史采样数组，并把所有元素初始化为 0.f。
        ...

        m_writePtr = 0;

        // m_readPtr 本质上等于 m_writePtr - m_delaySamples。
        // std::size_t 不能小于零，因此从环绕后的位置开始。
        m_readPtr = m_maxDelaySamples - m_delaySamples;
    }

    // 析构函数和其他成员……
    // 如果类拥有裸指针分配的内存，应删除复制与移动操作。

    bool process(float* buffer, std::size_t size)
    {
        // 在这里加入保护条件，避免未定义行为。

        for (std::size_t i = 0; i < size; ++i)
        {
            const float historySample = m_history[m_readPtr];
            m_history[m_writePtr] = buffer[i];
            buffer[i] = historySample;

            m_writePtr = (m_writePtr + 1) % m_maxDelaySamples;
            m_readPtr = (m_readPtr + 1) % m_maxDelaySamples;
        }

        return true;
    }

private:
    float* m_history; // 历史采样数组

    std::size_t m_maxDelaySamples = 0;
    std::size_t m_delaySamples = 0;

    std::size_t m_readPtr = 0;
    std::size_t m_writePtr = 0;
};

这样，一条漂亮、好用，而且采样精确的固定延迟线就完成了。它不依赖游戏线程，而是运行在音频回调线程中。只要音频线程没有被阻塞，这套实现就能稳定完成任务。

这个思路也很容易迁移到其他语言，有时语法反而更简单。例如在 Unity/C# 中，因为 C# 会自行管理数组长度，处理函数可以直接写成 bool process(float[] buffer)。当然，其他状态仍然需要自己维护。

可变延迟

固定延迟有很多用途，其中之一就是模拟声音传播。声音在任何介质中都有自己的传播速度；在普通空气中，声速大约是 343 m/s。如果希望游戏的声学体验更真实，模拟声音的传播时间是一项简单却很有效的细节。

在 Battlefield 或 Squad 这类大世界游戏中，远处的声音不一定会在事件发生的瞬间播放。比如一次爆炸，玩家大约要等待 距离 / 声速 的时间，才能听见它。

固定延迟在有限场景中可以做到这一点。如果声源和听者都保持不动，声音的传播时间就是固定的，固定延迟已经足够。但如果它们正在移动呢？声音传播到听者位置所需的时间会不断变化，这时固定延迟就失效了，可变延迟也因此登场。

可变延迟的作用就和名字一样直白：延迟时间可以在运行时改变。实现思路也不复杂。还记得 m_readPtr = m_writePtr - m_delaySamples 吗？这就是最核心的概念。我们仍然让读位置落后写位置 X 个采样，只不过现在的 X 会不断变化。

糟了！非整数采样怎么办？

想象一次发生在 400 m 外的爆炸。理想情况下，它产生的声音大约需要 1.166 秒 才能传到玩家的位置。我们的延迟以采样而不是秒为单位，因此第一步是把这段时间换算成采样数。

采样率每个采样的时长
44,100 Hz0.0226 ms
48,000 Hz0.0208 ms

在 48,000 Hz 的采样率下，每个采样大约持续 0.0208 ms。回到上面的例子，1.166 秒 大约等于 55,968 个采样。而根据实际距离计算出的结果，经常会落在两个整数采样之间。遗憾的是，数组并不支持 m_history[55968.4] 这样的分数索引。

好在我们可以对采样进行插值。每个采样之间的时间非常短，因此在这个场景下，可以把相邻采样之间的变化近似看作线性，再用线性插值得到中间值：

y[n] = x[nfloor] × (nceil − n) + x[nceil] × (n − nfloor)
C++ 
bool process(float* buffer, int size)
{
    // 其他保护条件与准备工作……
    ...

    for (int i = 0; i < size; ++i)
    {
        const unsigned indexA = static_cast<unsigned>(
            std::floor(m_readPositionInFloat));
        const unsigned indexB = (indexA + 1) % m_maxDelaySamples;

        const float fraction = m_readPositionInFloat
            - std::floor(m_readPositionInFloat);
        const float historyA = m_delayHistory[indexA];
        const float historyB = m_delayHistory[indexB];

        const float history = historyA * (1.f - fraction)
            + historyB * fraction;

        // 其他处理……
        ...
    }
}

以第 55968.4 个采样位置为例，我们先读取第 55968 和第 55969 个采样，再使用小数部分作为权重进行混合。如果两个采样值分别是 -0.3f 和 0.4f，插值结果就是 -0.02f。实际上，这个过程已经属于重采样，不过那又是另一个完整的话题了。

平滑延迟变化

继续用爆炸的例子。它发生在 400 m 外，当玩家站着不动时，声音需要大约 1.166 s 才能抵达。如果玩家主动朝爆炸位置移动，两者之间的距离会缩短，声音传播所需的时间也会随之减少。换句话说，我们正在不断减小延迟时间，也就是减少延迟采样数。

我们当然可以算出新的延迟，然后直接把读位置跳到那里，但更好的做法是对变化进行平滑。在音频编程中，任何突变都会造成波形不连续，最终产生咔哒声。因此，我们几乎总会让当前值平滑地靠近目标值。

实现过程很简单：每处理一个数据块，先计算目标延迟需要多少采样，再算出当前延迟在这个数据块的每个采样上应该增加或减少多少。

C++ 
bool process(float* buffer, int size)
{
    // 其他保护条件与准备工作……

    m_delaySamplesInFloat = getDelayInSamples();
    const float deltaDelay =
        (m_delaySamplesInFloat - m_currentDelayInFloat)
        / static_cast<float>(size);

    for (int i = 0; i < size; ++i)
    {
        // 分数采样读取与其他处理……
        ...

        m_writeIndex = (m_writeIndex + 1) % m_maxDelaySamples;
        m_readPositionInFloat = static_cast<float>(m_writeIndex)
            - m_currentDelayInFloat;

        if (m_readPositionInFloat < 0.f)
            m_readPositionInFloat += static_cast<float>(m_maxDelaySamples);

        // 每处理一个采样，就把延迟向目标推进一步。
        m_currentDelayInFloat += deltaDelay;
    }
}

目标延迟到采样数的换算很简单。使用原子变量后，其他线程可以更新所需的延迟值，而音频回调不需要为此加锁：

C++ 
float getDelayInSamples() const
{
    const auto delayInSeconds = m_delayInSeconds.load();
    return delayInSeconds * static_cast<float>(m_sampleRate);
}

这样，我们就得到了一条不会因为延迟变化而产生咔哒声的可变延迟线。

免费得到的多普勒效应

这套实现里，我尤其喜欢的一点是：它会自动为声音带来多普勒效应。当一个物体朝玩家移动时，延迟时间会不断减小。直观地说，读位置比写位置移动得更快，也就是我们用比平时更快的速度读过历史采样，因此音高会上升。

反过来，当物体远离玩家时，延迟时间会增加。读位置前进得更慢，音高也会下降。于是，同一套让声音传播时间保持合理的机制，也自然带来了人们熟悉的、随运动变化的音高偏移。
