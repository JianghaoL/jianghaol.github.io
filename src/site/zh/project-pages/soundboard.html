项目概述

SoundBoard 起源于一个很实际的工作流问题：设计师经常需要快速试听声音、测试交互参数，但如果每次都要打开游戏引擎集成，或在 Wwise 的多个界面之间来回切换，一次简单的创作判断也会被打断。

因此，我设计了这款能够通过 Wwise Authoring API 直接连接已打开项目的独立桌面工具。它会读取项目层级，并把每个声音对象所关联的控制集中展示出来。设计师不必依赖 Unity，就能实时试听 Event、调整 RTPC，或切换 Switch 状态。

我的目标并不是取代 Wwise，而是在它之上增加一层更专注的入口，让声音审阅时最常用的信息和操作能够立即被看到、被听到。

连接 Wwise

SoundBoard 启动时会先显示一个简洁的连接向导。只要 Wwise 项目已经打开，并在项目设置中启用了 WAAPI，工具就会建立连接并自动读取可用的声音对象。

我将连接步骤与主窗口分开，让应用当前所处的状态更清楚：在任何项目控制出现之前，用户能够先确认 Wwise 是否准备就绪；连接与数据载入的问题，也会被限制在一个简单明确的入口中。

更快速的项目导航

左侧面板会把连接到的 Wwise 项目转换为可展开的树状结构。文件夹、Switch Container 和普通声音对象拥有不同的视觉标记，即使项目规模变大，层级关系依然容易辨认。

我还加入了关键词搜索，以及隐藏 Wwise 2025 Factory 默认文件夹的选项。两种筛选都会从完整层级的保留副本中生成结果，因此用户可以随时更换搜索内容或恢复被隐藏的对象，无须重新向 Wwise 请求数据，也不会破坏原有结构。

让控制回到声音语境中

选择一个声音对象后，右侧详情面板会显示它在 Wwise 中的备注，以及相关的 Event、RTPC 和 Switch Group。Event 名称直接从项目中获取，每个播放按钮都会把对应事件发送给 Wwise Sound Engine。

RTPC 的范围会从曲线中自动读取，并转换成滑杆；用户既可以拖动控制，也可以直接输入数值。滑动产生的变化会经过轻量节流后再通过 WAAPI 发送，在维持即时反馈的同时，避免向 Wwise 提交过多重复更新。Switch 选项同样会被自动读取，并通过下拉菜单切换。

当这些关系被放在同一个界面里，设计师可以一边听见声音对象的实际表现，一边理解究竟有哪些参数正在驱动它。

开发方式

我负责定义产品方向、监督整体架构，并在开发过程中进行宏观层面的结构调整。在这一方向下，Avalonia 界面与 MVVM 架构的具体代码实现由 AI agent 完成。

Wwise Authoring API 的集成则由我独立完成，包括项目数据查询、Event 播放、RTPC 控制、Switch 切换和连接流程。将 WAAPI 通信放在独立的服务层中，也让 AI 实现的界面层与面向 Wwise 的核心逻辑可以分别迭代，而不会彼此紧密耦合。

考虑到设计师可能会在 SoundBoard 开启期间继续修改 Wwise 项目，我加入了 Refresh Project 功能，按需重新构建对象层级和控制数据。新增的 Event、RTPC 与 Switch Group 因此能够直接进入同一套工作流，无须重启应用。
