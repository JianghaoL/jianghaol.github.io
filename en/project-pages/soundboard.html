Overview

SoundBoard began with a simple workflow problem: designers often need to audition sounds and test interactive parameters, but opening an engine integration or moving through several Wwise views adds friction to a quick creative decision.

I designed a standalone desktop tool that connects directly to an open Wwise project through the Wwise Authoring API. It collects the project hierarchy and presents the controls attached to each sound object in one place, so events can be previewed and RTPC or Switch values can be tested in real time without relying on Unity.

The goal was not to replace Wwise. It was to create a focused layer on top of it—one that makes the parts most useful during sound review immediately visible and playable.

Connecting to Wwise

SoundBoard opens with a small connection wizard. Once a Wwise project is open and WAAPI is enabled in its project settings, the tool establishes the connection and loads the available sound objects automatically.

Keeping this step separate from the main window makes the application state clear: the user knows whether Wwise is ready before any project controls appear, while connection and data-loading errors remain contained in a simple entry point.

A Faster Way to Navigate

The left panel turns the connected Wwise project into a collapsible tree. Folders, Switch Containers, and regular sound objects use distinct visual markers, allowing the structure to stay readable even in a larger project.

I also added keyword search and an option to hide the Factory folders included with Wwise 2025. Both filters work from a preserved copy of the complete hierarchy, so users can change search terms or restore hidden content without querying Wwise again or losing the original structure.

Controls in Context

Selecting a sound object opens a detail panel with its Wwise notes, related Events, RTPCs, and Switch Groups. Event names are retrieved directly from the project, and each play button posts the corresponding event to the Wwise Sound Engine.

RTPC ranges are read from their curves and displayed as sliders, with both drag control and direct numeric entry. Slider changes are lightly debounced before being sent through WAAPI, keeping the response immediate without flooding Wwise with redundant updates. Switch options are also loaded automatically and can be changed from a dropdown.

Bringing these relationships into one view helps designers hear what an object does and understand what drives it at the same time.

Development Approach

I defined the product direction, supervised the overall architecture, and made the high-level structural adjustments throughout development. An AI agent handled the concrete implementation of the Avalonia interface and MVVM structure under that direction.

I implemented the Wwise Authoring API integration myself, including project queries, event playback, RTPC control, Switch changes, and the connection workflow. Keeping WAAPI communication behind dedicated services allowed the generated interface layer and the Wwise-facing logic to evolve without becoming tightly coupled.

Because the Wwise project may keep changing while SoundBoard is open, Refresh Project rebuilds the object hierarchy and control data on demand. Newly added Events, RTPCs, and Switch Groups can enter the same workflow without restarting the application.
