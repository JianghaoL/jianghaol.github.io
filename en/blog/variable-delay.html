Variable Delay in C++

From a sample-accurate fixed delay to fractional reads, smooth runtime changes, and a Doppler effect that emerges naturally.

Jianghao Li October 11, 2026 Audio Programming 9 min read

On this page

  1. Fixed Delay
  2. Variable Delay
  3. Non-integer Samples
  4. Smoothing Delay Changes
  5. The Doppler Effect

A delay line becomes much more interesting the moment its length can change. This article starts with the fixed-delay “string telephone” I built for Dreamcatchers, then extends the same ring-buffer idea into a smooth variable delay.

Fixed Delay

Recently I was working on Dreamcatchers, where I implemented a “string telephone” with a fixed-length delay. When the real-time voice data from players enters the buffer, the system holds it for X amount of time before playing it.

Naturally, there are two ways to make this happen. The first approach is simply to add a timer and only start feeding audio data into the output buffer once the timer stops. It is easy, but it depends heavily on the game’s main-thread timing. If the main-thread tick rate drops—for example, while handling a heavy rendering task—the timer can be inaccurate. It is the same situation in Unity: if you want sample-accurate timing, you do not want to count time in Update().

The second approach is a ring buffer. If you are familiar with audio programming, this is almost the default way to do it. Keep an array sized for the maximum delay, then maintain a delay sample count X, a read pointer, and a write pointer. The read pointer retrieves the historical sample first; the write pointer then overwrites that slot with newer data. Keep the read pointer X samples behind the write pointer, and you get an X-sample delay.

C++ 
class FixedDelay
{
public:
    FixedDelay(...) // Pass the parameters needed to initialize the members
    {
        // Dynamically allocate the history array and initialize it to 0.f.
        ...

        m_writePtr = 0;

        // m_readPtr is effectively m_writePtr - m_delaySamples.
        // std::size_t cannot go below zero, so start from the wrapped position.
        m_readPtr = m_maxDelaySamples - m_delaySamples;
    }

    // Destructor and other members...
    // Delete copy and move operations if the class owns a raw allocation.

    bool process(float* buffer, std::size_t size)
    {
        // Add guard clauses here to avoid undefined behavior.

        for (std::size_t i = 0; i < size; ++i)
        {
            const float historySample = m_history[m_readPtr];
            m_history[m_writePtr] = buffer[i];
            buffer[i] = historySample;

            m_writePtr = (m_writePtr + 1) % m_maxDelaySamples;
            m_readPtr = (m_readPtr + 1) % m_maxDelaySamples;
        }

        return true;
    }

private:
    float* m_history; // The history sample array

    std::size_t m_maxDelaySamples = 0;
    std::size_t m_delaySamples = 0;

    std::size_t m_readPtr = 0;
    std::size_t m_writePtr = 0;
};

This gives us a beautifully working, sample-accurate fixed delay. It does not depend on the game thread; it runs on the audio callback thread. As long as the audio thread is not blocked, it gets the job done nicely.

The idea transfers to other languages easily, sometimes with simpler syntax. In Unity and C#, for example, the process callback might simply be bool process(float[] buffer) because C# manages an array’s size internally. You still need to maintain the other state yourself.

Variable Delay

A fixed delay can be useful in many ways. One is to emulate the propagation of sound. Sound waves travel through every medium at a finite speed; in regular air, the speed of sound is approximately 343 m/s. If you want a more realistic acoustic experience in a game, emulating that travel time is a simple but effective detail.

In large-world games such as Battlefield or Squad, distant sounds do not necessarily play the instant an event occurs. An explosion reaches you after roughly distance / speed of sound seconds.

A fixed delay can achieve this in a limited scenario. If both the sound source and listener stay still, the travel time is fixed. But what if either of them moves? The propagation time changes continuously. That is where a fixed delay breaks down and a variable delay comes into play.

A variable delay does exactly what its name suggests: its delay time can change at runtime. The implementation is not complicated either. Remember m_readPtr = m_writePtr - m_delaySamples? That is the core concept. We are still keeping the read position X samples behind the write position, but now X can change.

Oh no! Non-integer Samples?

Imagine an explosion that starts 400 m away. Ideally, its sound takes about 1.166 seconds to reach you. Our delay works in samples rather than seconds, so we first have to convert that duration.

Sample rateMilliseconds per sample
44,100 Hz0.0226 ms
48,000 Hz0.0208 ms

At 48,000 Hz, every sample lasts about 0.0208 ms. In our example, 1.166 seconds becomes approximately 55,968 samples. The exact distance-derived result will often land between two whole sample positions, and an array has no built-in fractional index such as m_history[55968.4].

Thankfully, we can interpolate. Each sample represents such a short interval that a linear estimate between neighboring samples works well for this purpose:

y[n] = x[nfloor] × (nceil − n) + x[nceil] × (n − nfloor)
C++ 
bool process(float* buffer, int size)
{
    // Other guard clauses and setup...
    ...

    for (int i = 0; i < size; ++i)
    {
        const unsigned indexA = static_cast<unsigned>(
            std::floor(m_readPositionInFloat));
        const unsigned indexB = (indexA + 1) % m_maxDelaySamples;

        const float fraction = m_readPositionInFloat
            - std::floor(m_readPositionInFloat);
        const float historyA = m_delayHistory[indexA];
        const float historyB = m_delayHistory[indexB];

        const float history = historyA * (1.f - fraction)
            + historyB * fraction;

        // Other behavior...
        ...
    }
}

For sample position 55968.4, we read samples 55968 and 55969, then blend them using the decimal part. If the values are -0.3f and 0.4f, the interpolated value is -0.02f. This is, in fact, resampling—but that is a whole other topic.

Smoothing Delay Changes

Back to the explosion. It starts 400 m away and takes about 1.166 s to reach you while you stand still. If you move toward it, the distance shrinks, so the time it takes the sound to reach you also shrinks. In other words, we keep decreasing the delay time—or, here, the number of delayed samples.

We could calculate the new delay and jump the read position straight there, but it is better to smooth the change. In audio programming, an abrupt change creates a discontinuity in the waveform, which produces a click. We almost always want to move smoothly toward the target.

The process is simple: for each block, calculate the target delay in samples, then determine how much the current delay should increase or decrease on every sample in that block.

C++ 
bool process(float* buffer, int size)
{
    // Other guard clauses and setup...

    m_delaySamplesInFloat = getDelayInSamples();
    const float deltaDelay =
        (m_delaySamplesInFloat - m_currentDelayInFloat)
        / static_cast<float>(size);

    for (int i = 0; i < size; ++i)
    {
        // Fractional-sample read and other processing...
        ...

        m_writeIndex = (m_writeIndex + 1) % m_maxDelaySamples;
        m_readPositionInFloat = static_cast<float>(m_writeIndex)
            - m_currentDelayInFloat;

        if (m_readPositionInFloat < 0.f)
            m_readPositionInFloat += static_cast<float>(m_maxDelaySamples);

        // Move the delay toward its target once per sample.
        m_currentDelayInFloat += deltaDelay;
    }
}

The target conversion is small, and an atomic value lets another thread update the requested delay without making the audio callback take a lock:

C++ 
float getDelayInSamples() const
{
    const auto delayInSeconds = m_delayInSeconds.load();
    return delayInSeconds * static_cast<float>(m_sampleRate);
}

This gives us a smoothly changing delay without clicks.

The Doppler Effect Comes for Free

What I particularly like about this implementation is that it automatically adds the Doppler effect. When an object moves toward you, the delay keeps decreasing. Qualitatively, the read position moves faster than the write position, so the pitch rises because you are reading through the history faster than normal.

When the object moves away, the delay increases. The read position advances more slowly and the pitch drops. The same behavior that keeps propagation time physically plausible also gives the sound its familiar motion-dependent pitch shift.
