Overview

Cosmic Custodian reframes the classic box-pushing puzzle as a 3D sci-fi game. Players move through a grid, avoid dead corners, and push the box onto its destination. Three text-authored levels, a platform-aware tutorial, persistent audio settings, and a reusable event layer turn the compact puzzle loop into a complete game flow.

I developed the game in Unity 6.3.6 on macOS Sequoia 15.6.1. The project uses URP, Unity Input System, low-poly sci-fi environments and characters, a dedicated UI kit, interface sound effects, background music, and DOTween-driven motion.

Production Foundation

I assembled the project from modular environment, character, animation, UI, music, and sound-effect resources. DOTween provides the motion language for level construction and character movement, while the rest of the stack stays close to Unity's built-in workflows.

Keeping the presentation layer separate from the puzzle model made it possible to change art, timing, and feedback without rewriting the rules of the game.

Text-Driven Level Authoring

A Data-Driven Map Pipeline

Levels are authored in text files rather than assembled one object at a time. Each symbol maps to a wall, player, box, destination, or empty cell. ScriptableObjects hold the prefab and transform data needed to turn that notation into a three-dimensional scene.

LevelLoader reads LevelData/level_{n}.txt from Application.streamingAssetsPath, parses every character, and stores the resulting GridBlock objects in a Vector2Int-keyed dictionary. The repository currently ships three level files, so a puzzle can be revised without manually rebuilding the Unity scene.

Deterministic Initialization

Map generation depends on the active Game Config, and several singleton systems depend on one another during startup. To make that order visible and reliable, every participating class implements a small IInitializable interface.

InitializationManager sorts its Inspector entries, calls InitializeOnAwake synchronously in that order, then schedules each InitializeOnStart call after a short real-time delay. Empty default interface methods let a class opt into only the phase it needs.

Designer-Controlled Startup Order

Animated Map Construction

MapConstructor listens for LevelLoader's completion event and builds the board from the coordinate dictionary. Game Config stores the values that vary by level, so camera placement, support depth, timing, and prefab choices can be tuned without changing the constructor itself.

Each generated object rises into place through a DOTween coroutine. Randomized delays add a controlled rhythm while preserving the deterministic puzzle state underneath.

One Input Contract, Multiple Platforms

Desktop controls use Unity's Input System for movement, undo, restart, and pause. Mobile buttons implement IPointerDownHandler for touch input. PlatformManager derives the active mode from Application.isMobilePlatform; UIManager then selects the desktop or mobile UI handler, while TutorialManager displays platform-specific guidance. Both input paths still feed the same InputHandler request methods.

Cross-Platform Input

Event-Driven Gameplay

Gameplay systems coordinate through the static GameEventsManager instead of direct manager-to-manager references. Map loading, camera and UI state, movement, grid updates, single-step undo data, pause state, tutorial milestones, and win or loss checks all travel through focused UnityEvents.

This separation keeps input, animation, rules, and UI independently testable. It also makes platform-specific code a thin adapter instead of a second gameplay implementation.

Grid Logic Without Physics

The puzzle model is a dictionary from Vector2Int coordinates to block types: void, wall, player, box, or destination. PlayerMovementManager accepts only void, destination, or box cells. When a box is ahead, BoxMovementManager separately rejects a push whose next cell is a wall before any movement event is sent.

After validation, non-destination cells update immediately and DOTween moves the visible models. Destination cells keep their original type in GameDataManager, which allows WinLoseManager to recognize arrival after the animation. CommandManager stores the latest player and box coordinates and exposes one undo for the most recent move.

Move Validation & Undo

Lightweight Win & Dead-Corner Checks

After a box moves, WinLoseManager checks whether it reached a destination. For failure detection, the system gathers adjacent wall directions in a HashSet. More than two walls indicate a trapped U-shaped space; perpendicular wall pairs identify a corner from which the box cannot be recovered.

The algorithm avoids a full search while still catching the irreversible states most relevant to a compact Sokoban board.
