固定延迟

最近我在制作 Dreamcatchers 时，实现了一个带有固定长度延迟的“拉线电话”。当玩家的实时语音数据被送入缓冲区后，它会让输出延迟 X 时间再播放。

自然地，实现它有两种方式。第一种方法就是简单地加入一个计时器，只在计时器结束后才开始把音频数据送进输出缓冲区。这种方法很简单，但它高度依赖游戏主线程的计时；也就是说，如果主线程的 tick rate 因为某些原因下降了（例如正在处理繁重的渲染任务），计时器就可能给出错误的时间（这和 Unity 中的情况完全相同：如果你需要采样级精确的计时，就不会想用 Update() 来计时）。于是就有了第二种方式，也就是使用环形缓冲区。

如果你熟悉音频编程，这几乎就是默认的实现方式。思路很简单：保留一个大小等于所需最大延迟的数组，维护延迟采样数 X、一个读指针和一个写指针。读指针总是先从数组中读取历史采样，随后写指针再用新数据覆盖那个位置。怎样得到延迟呢？只要始终确保读指针落后写缓冲区 X 个采样，就会得到 X 个采样的延迟。

下面是一个 C++ 示例实现：

C++ 
class FixedDelay
{
public:
    FixedDelay(...) // You want to pass in all the parameters to initialize the private members
    {
        // You do need to dynamically allocate the array and set all element to 0.f
        // We're using a simple C-styled array here
        ...

        m_readPtr = 0;

        // Notice m_readPtr essentially equals to m_writePtr - m_delaySamples
        // I did this only because we used std::size_t which cannot go below 0
        m_readPtr = m_maxDelaySamples - m_delaySamples;
    }

    // Destructors, others...
    //
    // Explicitly delete copy and move constructors so we don't need to deal
    // with deep and shallow copy issues

    bool process(float* buffer, std::size_t size)
    {
        // Here you want some guard clauses just so you don't get UB

        for (std::size_t i = 0; i < size; ++i)
        {
            const float historySample = m_history[m_readPtr];
            m_history[m_writePtr] = buffer[i];
            buffer[i] = historySample;

            // Wraps the pointer so it stays in the array's range
            m_writePtr = (m_writePtr + 1) % m_maxDelaySamples;
            m_readPtr = (m_readPtr + 1) % m_maxDelaySamples;
        }

        return true
    }

private:
    float* m_history; // This is the history sample array

    std::size_t m_maxDelaySamples = 0;
    std::size_t m_delaySamples = 0;

    std::size_t m_readPtr = 0;
    std::size_t m_writePtr = 0;
};

这样，我们就得到了一个漂亮、好用而且采样精确的固定延迟效果。它不依赖游戏线程，而是依赖音频回调线程。只要音频线程没有被阻塞，它就可以很好地完成任务。这个思路也很容易迁移到其他语言，而且语法可能更简单。例如在 Unity/C# 中，你的 process 回调可以直接写成

C# 
bool process(float[] buffer);

因为 C# 会在内部管理数组的大小。不过，其他状态仍然需要手动维护。

可变延迟

固定延迟有很多用途，其中之一就是模拟声音传播。并不意外，声波在任何介质中都有自己的传播速度。在普通空气中，声速大约是 343m/s。在游戏中，如果你希望获得更真实的声学体验，模拟声音传播所需的时间是一件简单但很有效的事情。留意许多较大的世界游戏，比如 Battlefield 或 Squad，声音不会在事件触发时（比如爆炸）立刻播放；你要经过 距离 / 声速 的时间后才能听到。

固定延迟可以帮助你实现这一点——但只适用于有限的场景。如果发声声源和听者的位置都是固定的，那么声音传播所需的时间也是固定的，固定延迟就能完成任务。但是，如果它们在移动呢？在这种情况下，声音传播到听者位置所需的时间可能会不断变化。这时固定延迟就不再适用，可变延迟也就派上用场了。

可变延迟的作用很直白：它的延迟时间可以在运行时改变。实现思路也不复杂。还记得我们上面讨论过的 m_readPtr = m_writePtr - m_delaySamples 吗？这展示了最核心的概念。本质上，我们只是让读指针落后写指针 X 个采样。不过，要让它真正工作，还需要处理一些额外的问题。

糟了！非整数采样？

想象发生了一次爆炸，假设它最初距离你 400m。理想情况下，它产生的声音需要 1.166 秒 才能传播到你的位置。我们应该怎样计算延迟？还记得我们的延迟以 采样 而不是 秒 为单位吗？我们需要把时间换算成采样数。

采样率每个采样的毫秒数
441000.0226
480000.0208

从这个常用采样率表可以看到，当采样率为 48000 时，每个采样需要 0.0208ms。回到刚才的例子，1.166 秒 会换算成 55976.68 个采样。于是我们得到了一个不是整数的采样数！遗憾的是，现在没有（以后大概也不会有）用于数组分数索引的内置函数，让我们可以直接写出 m_history[55976.68]。好在从数学上说，我们可以对采样进行插值！因为每个采样所占的时间非常短，我们可以把相邻采样之间的变化看作线性，再在两个采样之间进行线性插值，得到一个近似值。

y[n] = x[nfloor] × (nceil − n) + x[nceil] × (n − nfloor)

稍微调整一下代码，我们会得到类似这样的实现：

C++ 
bool process(float* buffer, int size)
{
    // Other guard clauses and manipulations
    ...
    for (int i = 0; i < size; ++i)
    {
        const unsigned nFloor = static_cast<unsigned> (std::floor(m_readPtrInFloat));
        const unsigned nCeil = static_cast<unsigned> (std::ceil(m_readPtrInFloat)) % m_maxDelaySamples;

        const float fraction = m_readPositionInFloat - std::floor(m_readPtrInFloat);
        const float historyA = m_delayHistory[indexA];
        const float historyB = m_delayHistory[indexB];

        const float history = historyA * (1.f - fraction) + historyB * fraction; 

        // Other behaviors
        ...
    }
}

对于第 55976.68 个采样，我们取第 50657 和第 56058 个采样，再用小数部分在两者之间进行插值。假设 history[55976] = -0.3f，history[55977] = 0.4f，那么我们会得到 history[55976.68] = 0.183f。事实上，这就是重采样，不过那又是另一个完全不同的话题了。

平滑延迟变化

还是刚才的爆炸例子。我们说它发生在距离你 400m 的位置，声音需要 1.166s 才能到达你这里。这是在你保持不动的情况下。如果你正在主动朝爆炸位置移动呢？因为你与声源之间的距离正在减小，声音传播到你这里所需的时间也在减少！从定性的角度来说，我们正在减小延迟时间，也就是减少延迟采样数。

我们当然可以直接计算需要延迟多少采样，然后把 m_readPtr 设置到那个数值，但更好的做法是加入平滑处理。在音频编程中，任何突变都会让波形产生不连续，而这会造成点击声。我们几乎总是希望平滑地 lerp 到目标变化。这里的过程很简单：每处理一个数据块，就找出我们需要多少延迟采样，再计算当前延迟在每个采样上应该增加或减少多少。

下面的代码演示了这个过程：

C++ 
bool process(float* buffer, int size)
{
    // Other guard clauses and manipulations
    
    m_delaySamplesInFloat = getDelayInSamples();
    const float deltaDelay = (m_delaySamplesInFloat - m_currentDelayInFloat) / static_cast<float>(size);

    for (int i = 0; i < size; ++i)
    {
        // Our fractional sample implementation
        ...

        m_writeIndex = (m_writeIndex + 1) % m_maxDelaySamples;
        m_readPositionInFloat = static_cast<float>(m_writeIndex) - m_currentDelayInFloat;
        if (m_readPositionInFloat < 0) m_readPositionInFloat += static_cast<float>(m_maxDelaySamples);

        // Increase delay per sample
        m_currentDelayInFloat += deltaDelay; 
    }
}

其中 getDelayInSamples() 是：

C++ 
float getDelayInSamples() const
{
    const auto delayInSeconds = m_delayInSeconds.load(); // m_delayInSeconds is atomic<float> for thread safety
    return delayInSeconds * static_cast<float>(m_sampleRate);
}

这样，我们就得到了一个不会产生点击声、平滑且可变的延迟。

这套实现尤其好的一点，是它会自动为声音加入多普勒效应！当一个物体正在朝你移动时，延迟时间会不断减小。从定性的角度来说，这意味着读指针移动得比写指针更快。本质上，因为你读取的采样比平时更多，所以音高会上升。另一方面，如果这个物体正在远离你，延迟时间会减小，读指针的移动就会变慢，最终音高也会下降。
